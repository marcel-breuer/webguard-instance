# Monitoring Job Lease Protocol

This protocol lets multiple WebGuard Instances serve the same location without
deliberately executing one active monitoring job twice. It is versioned by its
Core instance-contract `v1` path and is opt-in in the instance through
`WEBGUARD_JOB_LEASES_ENABLED`.

## Core contract

All requests use the existing `X-API-KEY` and `X-INSTANCE-CODE` headers.
`instance_id` identifies a stable worker deployment or node; it must not reuse
the location code.

| Operation | Endpoint | Worker request | Core response or effect |
| --- | --- | --- | --- |
| Claim | `POST {instance API base path}/monitoring-jobs/claim` | `location`, `instance_id`, `capabilities`, `capacity`, `max_batch_size` | `jobs`, each with `job_id`, `phase`, `lease_expires_at`, `attempt`, `idempotency_key`, and a monitoring snapshot |
| Complete | `POST {instance API base path}/monitoring-jobs/{job_id}/complete` | `attempt` and one normalized `result` | Completes the lease and records the result once for the `Idempotency-Key` header |
| Extend | `POST {instance API base path}/monitoring-jobs/{job_id}/extend` | `attempt` | Returns the new `lease_expires_at` when a long-running check needs more time |
| Release | `POST {instance API base path}/monitoring-jobs/{job_id}/release` | `attempt` and a machine-readable reason | Makes a job eligible for later placement without recording a result |

`phase` is one of `response`, `ssl`, or `domain_expiration`. This makes the
existing response and certificate checks for one monitoring separate schedulable
jobs. Core must assign at most one unexpired lease for a job. It may return a
mixed batch and must cap it at the lesser of its own backpressure limit,
`capacity`, and `max_batch_size`.

The completion idempotency key is generated by Core for the claim attempt. Core
must treat repeated completion requests bearing that key as the same logical
result. Expired leases become claimable again with a new attempt and key.

## Instance behavior

The instance supplies all supported phases as capabilities and uses the shared
execution limiter for every claimed job. It completes jobs that produce a
normalized result, including `down` and `unknown` outcomes. It releases jobs it
cannot execute, such as an unsupported phase/type combination or cancellation
before execution. A transport failure while completing is not released: Core
can safely accept a retry with the same idempotency key, or reissue work after
the lease expires.

## Rollout and rollback

1. Deploy the Core endpoints while existing polling remains enabled.
2. Deploy Instances with `WEBGUARD_JOB_LEASES_ENABLED=false` and a configured,
   stable `WEBGUARD_INSTANCE_ID`.
3. Enable `WEBGUARD_JOB_LEASES_ENABLED=true` for a small worker group. Set
   `WEBGUARD_JOB_LEASES_DUAL_WRITE=true` only if Core needs to compare the
   legacy result streams during migration.
4. Verify Core records a single logical result per idempotency key and that
   lease expiry requeues unfinished jobs. Expand the worker group, then disable
   dual write.
5. To roll back, set `WEBGUARD_JOB_LEASES_ENABLED=false`. The worker resumes
   the unchanged legacy polling and result endpoints; unexpired leases are
   allowed to expire before Core reassigns them.

The legacy endpoints remain available until all compatible Core and Instance
deployments use the lease protocol.
